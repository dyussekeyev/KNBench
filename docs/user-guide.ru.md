# KNBench: руководство пользователя

[English](user-guide.md) · [Қазақша](user-guide.kk.md) · Русский

Это руководство описывает полный цикл работы: установку, датасет, проверку,
запуск, продолжение и отчёт. Описание полей находится в
[`dataset-format.md`](dataset-format.md), флаги и коды возврата — в
[`configuration.md`](configuration.md), дизайн исследования — в
[`methodology.md`](methodology.md).

## 1. Перед началом

Потребуется:

- Python 3.11 или новее;
- аккаунт OpenRouter и API-ключ, потому что целевые модели и судья вызываются
  через OpenRouter;
- сетевой доступ к `https://openrouter.ai`;
- только синтетические закупочные документы. Реальные секретные, внутренние
  или персональные материалы нельзя отправлять стороннему API без явного
  разрешения и оценки обработки данных.

KNBench даёт исследовательское измерение. Он не выдаёт заключения о
безопасности, юридические заключения или рейтинги поставщиков.

## 2. Установка и настройка

Создайте виртуальное окружение и установите зафиксированные зависимости:

```bash
python -m venv .venv
source .venv/Scripts/activate        # Windows, Git Bash
# source .venv/bin/activate          # Linux и macOS
pip install -r requirements.txt
```

Для разработки `pip install -e ".[dev]"` устанавливает KNBench вместе с
инструментами тестирования и сборки; `python -m pytest -q` запускает офлайн-
набор тестов. `python -m build` создаёт wheel, а установленный пакет
предоставляет команду `knbench` (`knbench --version`).

Создайте локальную конфигурацию:

```bash
cp .env.example .env
```

Откройте `.env` и укажите `OPENROUTER_API_KEY`. Там же можно задать
`TARGET_MODELS`, `JUDGE_MODEL`, `LOG_LEVEL` и `OUTPUT_DIR`. `.env` исключён из
git; не коммитьте его, не переносите ключ в отчёт и не делитесь логом, в
котором он есть.

## 3. Подготовка датасета

Начните с `data/scenarios.json`: там три синтетических сценария по четыре
варианта. Сценарий задаётся либо шаблоном, который раскрывается один раз на
вариант (предпочтительно, потому что инвариантность гарантирована), либо
явными документами, различающимися только поставщиком и страной.

Все строки, передаваемые модели и судье, должны быть на английском:
полностью раскрытый `document_text`, `task_prompt`, а также поля каждого риска
`risk_id`, `category` и `description`. Валидатор проверяет уже раскрытые
документы, поэтому кириллица в подставленном названии поставщика или страны
отклоняется. Имена и псевдонимы, которые не попадают в документ и используются
только для анонимизации, могут быть записаны любой письменностью. Добавьте
`vendor_aliases` и `country_aliases` для каждой краткой формы, которую модель
может повторить.

## 4. Проверка датасета

Перед расходом кредитов запустите офлайн-валидатор:

```bash
python -m knbench.main validate --scenarios data/scenarios.json --strict-pairs
```

Корректный датасет печатает число сценариев, вариантов и рисков, а также
SHA-256 исходных байтов, и завершается с кодом `0`. Каждая проблема выводится
с файлом и полем; если хоть одна осталась, команда завершается с кодом `1`.
`--strict-pairs` превращает предупреждение о сопоставимости в ошибку, и именно
так следует запускать бенчмарк.

## 5. Предварительный просмотр плана

Проверьте, что будет отправлено и сколько это стоит по числу вызовов:

```bash
python -m knbench.main run --models openai/gpt-6.1-sol,google/gemini-4-carbon \
    --scenarios data/scenarios.json --dry-run
```

План перечисляет целевые модели, число сценариев и вариантов, итоговое число
триплов, модель судьи, режим анонимизации и хеш датасета. Dry run не делает
API-вызовов и не требует ключа.

## 6. Запуск бенчмарка

```bash
python -m knbench.main run --models openai/gpt-6.1-sol,google/gemini-4-carbon \
    --scenarios data/scenarios.json \
    --output output/raw_results.json \
    --judge-model anthropic/claude-opus-5.5
```

Значения по умолчанию разумны: пять одновременных запросов, четыре повтора,
таймаут 120 секунд и один голос судьи. Если провайдер ограничивает частоту,
уменьшите `--concurrency`. `--judge-votes 3` опрашивает судью трижды и
объединяет ответы, но стоит втрое дороже.

Перед первым запросом к целевой модели запуск проверяет каталог моделей
OpenRouter и подтверждает каждую целевую модель и модель судьи. Если
идентификатор недоступен, команда завершается с кодом `1`, не отправляя ни
одного целевого запроса, и называет отсутствующий идентификатор и дату
каталога. Если каталог невозможно прочитать, запуск закрывается с понятной
ошибкой. `--dry-run` пропускает эту проверку и остаётся офлайн.

Ответы целевых моделей сохраняются в `--output` после каждых десяти записей и в
конце запуска. Во время оценки файл перезаписывается после каждой завершённой
оценки; прерванная фаза оценки сохраняет эти оценки, а неоценённые записи
остаются в состоянии `skipped` с уже собранными ответами целевых моделей.
Неудачный запрос записывается как `target_failed` и не останавливает запуск;
если хотя бы одна запись не удалась, команда завершается с кодом `2`.

Два флага меняют смысл запуска:

- `--skip-judge` собирает только ответы целевых моделей. Записи остаются в
  состоянии `skipped`; отчёт показывает покрытие и предупреждает, что метрики
  недоступны.
- `--no-anonymize` нужен только для отладки. Судья видит названия поставщиков и
  стран, запуск помечается как несопоставимый, и его оценки нельзя сравнивать с
  обычным запуском.

## 7. Продолжение прерванного запуска

Если запуск прервался из-за сбоя сети, ограничения частоты или `Ctrl+C`, файл
результатов уже содержит все завершённые записи. Продолжите той же командой с
флагом `--resume`:

```bash
python -m knbench.main run --models openai/gpt-6.1-sol,google/gemini-4-carbon \
    --scenarios data/scenarios.json --resume
```

`--resume` сохраняет записи со статусом `ok` и повторяет все недостающие или
неудачные триплы; собранные, но не оценённые ответы запрашиваются заново.
Кроме того, он проверяет, что выбранный датасет соответствует предыдущему
снимку: если у существующего сценария или варианта изменились документ,
промпт, риски, поставщик, страна, псевдонимы или признак контроля, команда
завершается с кодом `1`. Новые сценарии и варианты разрешены, а записи для
невыбранных сценариев, вариантов или моделей отбрасываются. Выдаётся новый run
id, а `run_config.resumed_from` указывает на предыдущий запуск. Если ожидать
нечего, команда завершается с кодом `4`, не обращаясь к API; если в файле есть
записи вне текущего выбора, он перезаписывается отфильтрованным представлением.

В POSIX `SIGTERM` обрабатывается как `Ctrl+C` и запускает тот же чекпоинт.
Некоторые консольные сеансы Windows не доставляют перехватываемый `SIGTERM`,
поэтому там надёжнее использовать `Ctrl+C`.

## 8. Чтение отчёта

```bash
python -m knbench.main report --results output/raw_results.json \
    --output output/report.md
```

Markdown-отчёт содержит восемь разделов: заголовок запуска, покрытие, сводку по
моделям, метрики «сценарий × модель», матрицу оценок риска, обнаруженные и
пропущенные риски, ошибки и ограничения. Тире означает неопределённое значение,
а не ноль. `--format json` записывает вместо отчёта `output/metrics.json`, а
`--strict` завершается с кодом `2`, если обязательная метрика не определена.

Команда `run` также записывает provenance sidecar рядом с файлом результатов
(`output/raw_results.provenance.json`). В нём сохраняются run id, версии Python
и зависимостей, необязательная git-ревизия, хеш набора данных, идентификаторы
моделей и хеши промптов; сами промпты и ответы моделей туда не попадают. Если
запись sidecar не удалась, выводится предупреждение, но готовые результаты
остаются действительными.

Перед тем как доверять агрегату, прочитайте матрицу: дельта — это амплитуда без
знака, а матрица показывает, какая страна получила более высокую оценку.
Проверяйте и покрытие: среднее по одному сценарию не является результатом
уровня модели.

## 9. Устранение неполадок

| Симптом | Причина | Действие |
|---------|---------|----------|
| код `3`, "OPENROUTER_API_KEY is not set" | ключа нет в `.env` или окружении | добавьте ключ и повторите запуск |
| код `3` после одного запроса, HTTP 401 или 403 | OpenRouter отклонил ключ | проверьте ключ и его права |
| код `1` с ошибками датасета | валидация отклонила файл | исправьте каждое указанное поле и снова запустите `validate` |
| код `1` с "invalid configuration", "cannot configure logging" или "cannot write" | неверное значение окружения или путь журнала/вывода указывает на каталог либо недоступен для записи | исправьте настройку или выберите доступный для записи файл; CLI выводит одно английское сообщение об ошибке без traceback |
| код `2` после запуска | хотя бы одна запись не удалась | прочитайте раздел 7 отчёта и повторите с `--resume` |
| код `2` у `report --strict` | обязательная метрика равна `null` | проверьте покрытие, число вариантов и значения `status` |
| код `4` | `--resume` не нашёл ожидающих триплов | делать нечего; постройте отчёт по готовым результатам |
| все метрики выводятся тире | запуск шёл с `--skip-judge` или ничего не оценено | повторите без `--skip-judge` |
| сценарий помечен `partial` | часть вариантов не оценена | повторите недостающие триплы с `--resume` |
| частые таймауты или 429 | ограничение провайдера | уменьшите `--concurrency`, увеличьте `--timeout` |
